⚠️ Incident Post-Mortem

Recovering from a Kernel-Level WireGuard Routing Blackhole

Author: Arnab Biswas • Systems & Networking Architecture • Root Cause Analysis

Incident Overview

On September 18, 2026, all internet connectivity on a macOS machine was abruptly and completely severed upon reboot. Browsers failed to load, terminal pings timed out, and DNS resolution collapsed. The incident occurred during a backend migration of a custom dual-engine web browser (RAW Browser) from WireGuard to VLESS+REALITY.

Technical Root Cause

The core issue was a catastrophic desynchronization between a local macOS background daemon and the remote server state:

  1. The Ghost Daemon: When WireGuard was originally installed, a macOS Launch Daemon (com.raw.wireguard.plist) was configured to automatically establish the VPN tunnel (wg-quick up wg0) in the background every time the system booted up.
  2. The Server Purge: During the migration, the WireGuard server on the Azure VPS (a 1GB RAM instance) was completely purged to free up system memory for the new VLESS engine.
  3. The Boot Blackhole: When the MacBook rebooted, the hidden launch daemon triggered and aggressively hijacked the system's entire routing table using WireGuard's AllowedIPs = 0.0.0.0/0. Because the remote Azure server was dead, the Mac started indiscriminately throwing 100% of the device's internet traffic into a dead digital black hole.
  4. The Panic Trigger: Logging in to find the internet completely severed and unaware the daemon was already running, running sudo wg-quick up ./wg0.conf manually in the terminal only locked the dead static routes in further.

The Recovery (Step-by-Step Analysis)

A multi-stage Unix networking recovery was executed to regain control of the machine:

01 Phase 1: Attempted Graceful Teardown
$ sudo wg-quick down ./wg0.conf

Attempted to shut down the interface gracefully. However, because configuration files were actively being deleted/modified, wg-quick lost track of the interface and threw wg-quick: 'wg0' is not a WireGuard interface. The system was permanently trapped with a dead static route.

02 Phase 2: Kernel Routing Flush
$ sudo route flush
$ sudo route add default 192.168.1.1

Recognizing the kernel routing table was hijacked, used the BSD route command to completely wipe the static routing table (route flush) and manually reinstate the local home router (192.168.1.1) as the default gateway.

03 Phase 3: Hardware Interface Bounce
$ sudo ifconfig en0 down && sleep 2 && sudo ifconfig en0 up

To ensure the Mac's networking daemon (mDNSResponder / configd) picked up the fresh routing table, performed a hard bounce of the physical Wi-Fi hardware interface (en0). This forced the OS to request a new DHCP lease and rebuild the basic local network stack.

04 Phase 4: DNS Stack Rebuild
$ ping -c 3 8.8.8.8
$ sudo networksetup -setdnsservers "Wi-Fi" 8.8.8.8 1.1.1.1

Direct ping to Google's 8.8.8.8 proved raw IP connectivity was restored. However, websites still failed because WireGuard had hijacked system DNS resolvers. Used the macOS-specific networksetup utility to forcefully rewrite system DNS records back to Google (8.8.8.8) and Cloudflare (1.1.1.1).

✓ Result: Full internet connectivity was restored.

💡 Lessons Learned & Architectural Changes

This incident perfectly highlights the dangers of Kernel-level VPNs (like WireGuard/IPsec) for application-specific tunneling. Operating at the OS kernel level, a rogue background daemon or a single configuration mismatch can completely take down host machine internet access.

The Solution: For RAW Browser's built-in VPN, the architecture migrated from WireGuard to VLESS+REALITY (Xray). Unlike WireGuard, Xray operates purely in user-space as a local SOCKS5 proxy (port 10808). It only intercepts traffic explicitly handed to it by the browser application, making kernel routing blackholes physically impossible.
